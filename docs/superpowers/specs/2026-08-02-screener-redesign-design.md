# 市场筛选器重构设计文档（合约小市值双向筛选）

**日期**: 2026-08-02
**状态**: 已确认
**路由**: `/[locale]/screener`（沿用现有路由，替换内部实现）

---

## 背景

现有 screener（见 [2026-07-28-screener-design.md](./2026-07-28-screener-design.md)）存在以下问题：

1. 只能单方向筛选（写死 `direction: "long"`），无法同时看到做多/做空两组候选
2. 现货/合约切换按钮不影响数据源（始终读现货 ticker），但 OI、资金费率是合约专属概念，语义错位
3. 打分模型里"流动性"维度奖励大成交量，天然偏向主流大币，与"倾向小币种做日内短线"的目标相反
4. 只能手动刷新，没有定时自动重新筛选

本次重构目标：只做合约市场，引入市值分层排除主流大币，新增方向性信号，同时输出"做多优势"和"做空优势"两组 Top 10，并支持每小时自动重新筛选。

---

## 目标与范围

- 只做**合约（Futures）**市场，去掉现货/合约切换 UI
- 候选池排除**市值前 50** 的主流币；剩余候选按市值越小加分越高
- 每 **1 小时**自动重新筛选一次（客户端定时 refetch），同时保留手动「立即刷新」按钮
- 输出两组，各 **Top 10**：做多优势 / 做空优势，页面左右并排展示

---

## 数据架构

### 新增/修改数据源

| 数据 | 来源 | 说明 |
|---|---|---|
| 合约 24h 行情（批量） | 新增 `getFuturesTickers()`，调用 `/openApi/swap/v2/quote/ticker`（不传 `symbol`） | 现有 `getFuturesTicker(symbol)` 只支持单个查询；批量接口沿用现货 `getSpotTickers()` 同款"不传 symbol 即返回全部"的约定（见 [market.ts:47](../../../src/lib/bingx/market.ts)） |
| **现货 24h 行情（批量）** | 复用 `useSpotTickers()` | **只用来取真 24h 涨跌**，不作为筛选标的来源。原因见下方「实测发现的 BingX 数据陷阱」第 1 条 |
| 市值数据 | 新增服务端路由 `GET /api/market-cap`，调用 CoinGecko `GET /coins/markets?vs_currency=usd&order=market_cap_desc&per_page=250`（拉 4 页，共约 1000 个币） | 服务端 `fetch` 设置 `next: { revalidate: 3600 }`（1 小时）。**必须校验结果覆盖到市值前 50 名**（`hasTopRankCoverage`），否则返回 502 让前端走中性分兜底——第 1 页装的正是排除规则要拦的那批币，缺了它会静默放行大币 |
| OI / 资金费率 | 复用现有 `getFuturesOpenInterest(symbol)` / `getFuturesFundingRate(symbol)` | 仍按候选池逐个并行请求，但**并发上限 8**，且候选池必须等现货数据落地后才计算（否则会打两轮全池请求） |

### Symbol 映射策略

CoinGecko 返回的 `symbol` 字段（如 `pepe`）可能被多个币种共享。策略：

1. 按 `market_cap_desc` 排序遍历，同一 `symbol` 只保留第一次出现（即市值最高）的映射
2. 匹配键：`BINGX_SYMBOL = coingecko_symbol.toUpperCase() + "-USDT"`
3. 若某个 BingX 合约在 CoinGecko 前 1000 名里查不到对应市值 → 不淘汰，视为"市值排名靠后/未知的极小盘"，市值维度直接给满分
4. 若 `/api/market-cap` 整体请求失败 → 不阻塞筛选流程，市值维度统一退化为默认 50 分，页面显示小提示

### 三阶段筛选流程

1. **第一轮（批量）**：拉取全量合约 ticker → 硬性淘汰（流动性、振幅、涨跌幅方向阈值）
2. **第二轮（市值过滤）**：结合市值 map → 排除市值前 50 的币 → 得到"小币候选池"（做多/做空各一份，因为方向阈值不同）
3. **第三轮（按需详情）**：对两份候选池的并集并行请求 OI + 资金费率 → 分别计算做多/做空评分 → 各自排序取 Top 10

## 硬性淘汰规则（一票否决，方向相关）

沿用现有 `hardFilter` 的规则，数据源改为合约 ticker：

| # | 规则 | 说明 |
|---|---|---|
| 1 | 24h 成交额 < **$7M**（`MIN_QUOTE_VOLUME`） | 见下方数据陷阱第 3 条——不要往回调 |
| 2 | 24h 振幅 < 1.5% | 死盘无波动 |
| 3 | 做多方向：24h 涨幅 > +15% | 拒绝追高。**24h 涨跌未知时此规则不生效**（拿不到数据不能断言它暴拉过） |
| 4 | 做空方向：24h 跌幅 < -15% | 拒绝追空，同上 |
| 5 | 市值排名 ≤ 50 | 排除主流大币；**市值未知不算淘汰** |
| 6 | 市值 > **$500M**（`MAX_MARKET_CAP`） | 见下方「排序方式」——按分差排序后市值在排名里会被抵消，小市值取向只能靠门槛守住 |
| 7 | 代币化合成品（`NCSK`/`NCCO`/`NCSI`/`NCFX` 前缀） | BingX 永续里混了 391 个代币化股票/商品/指数/外汇，它们不是加密货币。用四个明确前缀而非裸 `NC`，避免误伤 `NCASH` 这类真实币 |

规则 5、6 在市值 map 整体为 `null`（数据不可用）时**一律不生效**——数据缺失绝不能把榜单清空。

## 打分模型（0-100 分，做多/做空分别计算一份）

流动性维度从"加权评分"改为"硬性门槛"（规则 1），不再在评分里额外奖励大成交量，避免与"偏向小币种"目标冲突。

| 维度 | 权重 | 逻辑 |
|---|---|---|
| **市值（越小越优）** | 25% | `log10(marketCap)` 反向归一化：市值 ≤$10M → 100 分，≥$2B → 0 分，区间内线性插值；市值未知 → 100 分 |
| **振幅** | 20% | 沿用现有逻辑：2-5% 最优（满分）；1.5-2% 线性爬升；>12% 递减至 0 |
| **资金费率方向信号** | 20% | 做多组：费率越负（空头拥挤，潜在轧空）分越高；做空组：费率越正（多头拥挤，潜在轧多）分越高；方向不利时给低分 |
| **OI/成交量比** | 15% | 沿用现有逻辑：0.3-1.5 最优区间，>3 判定持仓过重给 0 分 |
| **24h 动量方向匹配** | 10% | 以 **+3% 为峰**的倒 U：走平（0%）和数据未知都落在中性 50，逆向走势降到 -15% 时归零，追高到 +15% 也归零。做空组符号相反 |
| **趋势位置** | 10% | 方向感知：做多希望价格在日内区间偏下半段（`eff` 0.2-0.5 满分），做空反向 |

**「未知」的统一策略**——三种缺失必须彼此自洽，否则筛选器会系统性偏爱它了解最少的币：

| 缺失项 | 给分 | 理由 |
|---|---|---|
| 市值查不到 | 100 | 比 CoinGecko 第 1000 名还小，确实是极小盘 |
| 24h 涨跌拿不到 | 50（中性） | 与「走平」同分。早期版本给 50 而走平给 0，导致没有现货对的币凭空胜过真实走平的币 |
| 持仓量拿不到 | 50（中性） | 早期版本给 0，使「请求失败」和「真的是 0」无法区分，OI 部分失败时排名纯按请求运气重排 |

**关于短期动量的取舍**：真正的短期动量信号（如拉 1h/4h K 线计算斜率）需要对候选池每个币额外发一轮请求。当前用现货的 24h 涨跌做代理，不新增第四轮请求。

## 排序方式：按方向分差（edge），不是按绝对分

两组各自的排序键是 **`edge` = 当前方向分 − 反方向分**，只保留 `edge > 0` 的币。

**为什么不能按绝对分排**：六个维度里 60% 不分方向（市值 25% + 振幅 20% + OI 15%）。实测候选池只有约 40 个币时，这 60% 的「这币本身好不好」直接主导两份排名，结果两组 Top 10 里 **9 个是同一批币**——同一个币被同时标成「做多优势」和「做空优势」，两份榜单失去意义。

按分差排序后两组**结构性互斥**：同一个币的两个 edge 互为相反数，而两组都要求 `edge > 0`，一个数和它的相反数不可能同时为正；恰好相等时两边都排除。

**代价（务必知道）**：分差把那 60% 的共同项完全抵消了，排名实际上只由方向性维度决定，等价于 资金费率 50% / 动量 25% / 趋势位置 25%。**市值因此不再影响排名，只剩门槛作用**——这就是必须引入 `MAX_MARKET_CAP` 硬性上限的原因，否则会出现 $1.2B 的币登上小市值筛选器榜首（实测确实发生过：BEAT $1.12B、1000PEPE $1.20B）。

## 实测发现的 BingX 数据陷阱

以下四条都是**跑起来看真实榜单**才发现的，代码审查一条都没抓到。改动这块之前先读：

1. **合约 ticker 的 `priceChangePercent` 不是 24h**，而是约 3.2 分钟的滚动窗口（实测 `openTime→closeTime` = 3.21 分钟，同一份响应里现货是正好 1440.00 分钟）。全市场 765 个合约中位数为 0，只有 8 个超过 1%，最大值 25 亿（垃圾值）。同一响应里 `highPrice`/`lowPrice`/`quoteVolume` **确实是 24h**。所以 24h 涨跌必须从现货取，按剥掉乘数前缀后的 symbol 关联（实测覆盖率约 60%）。

2. **合约乘数前缀**：BingX 把 SHIB 的千倍合约挂成 `1000SHIB-USDT`，这类共 10 个（`1000PEPE`、`10000SATS`、`1000000BABYDOGE` 等）。查市值/关联现货前必须过 `stripContractMultiplier`，否则 SHIB、PEPE 这些前 50 大币会被当成「查不到市值的极小盘」，既绕过排除又拿满分。正则只剥 `1` 后跟 3 个以上 `0`——`1INCH`、`0G`、`2Z`、`4` 是真实币名，不能动。

3. **长尾的 `quoteVolume` 被拍平**：516 个真实加密货币永续里，**144 个的成交量全挤在 6,185,710–6,913,330 这个 0.73M 宽的带里**。真实成交量是幂律分布，不可能长这样。头部正常（BTC 557M、ETH 383M、SOL 167M、AAVE 56M）。所以门槛定在 $7M——刚好跨过整条假带。定 $5M 会正好卡在假数据中间。（`quoteVolume` 本身确实是 24h：用 24 根小时 K 线求和交叉验证，比值 1.015–1.024。）

4. **代币化合成品混在永续列表里**：907 个 USDT 永续中 391 个是 `NCSK` 股票（311）、`NCCO` 商品（27）、`NCSI` 指数（15）、`NCFX` 外汇（38）。它们在 CoinGecko 查不到市值，于是「查不到 = 极小盘 = 100 分」这条规则给了它们 25% 权重的满分——实测**曾把 Tesla、Oracle、Palantir、PayPal 送上榜单，20 个结果里 19 个是股票**。

## 页面布局

### 布局结构

```
┌────────────────────────────────────────────────────────────────────┐
│  市场筛选器（合约）                    下次刷新: 42:15  [立即刷新]  │
├──────────────────────────────┬───────────────────────────────────┤
│  做多优势 Top 10               │  做空优势 Top 10                   │
│  # 币种 价格 涨跌 振幅 市值    │  # 币种 价格 涨跌 振幅 市值        │
│    成交量 OI/量 费率 评分 优势  │    成交量 OI/量 费率 评分 优势      │
│    [做多]                      │    [做空]                          │
│  ... 10 行 ...                 │  ... 10 行 ...                     │
└────────────────────────────────────────────────────────────────────┘
```

- 桌面端左右并排；窄屏（移动端）自动堆叠为上下两块，各自可横向滚动查看列
- 表格内**不再支持点击排序**：两组已经是按综合评分排好的 Top 10，允许排序会打乱"综合最优"的语义
- 每行只保留**单一方向**的操作按钮：做多组只有"做多"按钮（跳转 `/trade?symbol=X&side=long&market=futures`），做空组只有"做空"按钮
- 顶部显示距下次自动刷新的倒计时，「立即刷新」按钮可随时手动触发三轮数据重新拉取

### 加载 / 空 / 错误状态

- 两个表格分别显示各自的骨架屏（10 行）和空状态文案（例如做多组因门槛严格可能不足 10 个，做空组不受影响，二者独立展示）
- 市值数据加载失败：不阻塞整体展示，市值维度退化为默认 50 分，页面给出小提示
- 合约 ticker / OI / 资金费率任一请求彻底失败：显示错误态 + 重试按钮（沿用现有错误处理模式）

## 组件与状态管理

不引入新的 Zustand store，页面内用 `useState`（当前 tick / 倒计时展示）+ React Query 的 `refetchInterval`（1 小时）驱动自动刷新，`useMemo` 派生筛选和打分结果。
